# Этап 6 — робот-отклик на hh.ru (🚀) + статусы откликов и чаты HR

**Цель:** нажатие 🚀 под письмом → робот сам откликается на hh с этим письмом и отчитывается в том же сообщении. Плюс
(робот всё равно вошёл в hh): статусы откликов (просмотр / приглашение / отказ) и сообщения HR в Telegram.

**Почему так.** Отклик вручную (этап 4) — рутина: 36 откликов за 4 дня, до 20 в день. API соискателей hh закрыт с
15.12.2025 → только браузер (путь C, CLAUDE.md §4; автоматизация против правил hh — риск ограничений аккаунта принят).
Теневой режим (10.10.2026): 60 пар оценок, совпало 25 (42%), нейросеть поймала 12 из 39 откликов пользователя →
робот **сам не решает**, только по кнопке. Разбор теневого режима — отдельно, после робота.

## Принципы

1. **n8n — оркестратор и единственный источник бизнес-состояния** (очередь, статусы, лимит, уведомления).
   **applier — исполнитель**: знает только браузер и hh, хранит то, что живёт в браузере (сессия, открытая капча), и
   предохранители, которые держат даже при ошибке в n8n.
2. **Один писатель:** переходы очереди (`apply_state`) делает только W9; W3 и W7 передают команды.
3. **Безопасно по умолчанию:** `APPLY_LIVE=0`, `apply.enabled=false`; необратимое — только через `act()`; одно действие за раз.
4. **hh — истина:** «уже откликались» проверяется перед кликом → любой повтор безопасен.
5. **Сеть важнее DOM:** исход — по ответам API, которые делает сам интерфейс hh; знание hh — в `applier/src/hh/`.
6. **Непонятно → человеку:** неясный исход возвращает вакансию в ✅ с пометкой; ручной 📝 работает всегда.

```

W5 Letter: письмо с 🚀, если можно                              ▲   └── вызывает себя после успеха
W7 ⚙️ 🚀 Робот ──(выключили → очередь назад; сняли паузу → tick)─┘

W9 / W10 / W7 / W6 ──HTTP, X-Applier-Token──▶ applier:3000 (job-hunter-applier)

CLI scripts/applier.mjs ──▶ 127.0.0.1:5682
```

### Робот `applier/` (Node.js, Playwright)

| Слой | Файлы | Что делает |
|---|---|---|
| http | `src/server.mjs` | адреса, токен `X-Applier-Token`, замок (одно действие за раз: занято → 409, блок → 423), фоновые задания, обслуживание, мягкая остановка |
| сессия | `src/browser.mjs` | Chromium с окном, профиль `/data/profile`; бэкап `storageState` после входа и раз в час (сессионные cookie Chromium не хранит) + восстановление; перезапуск раз в сутки в 05:00 по Таиланду; сетевой предохранитель (`guardAllow` — открыть одно действие); скриншоты JPEG |
| состояние | `src/store.mjs` | блок (капча, вход, лимит hh, сбои) и счётчики «дня» — `/data/state.json`; последний результат по вакансии — в памяти на сутки |
| hh | `src/hh/selectors.mjs`, `src/hh/state.mjs`, `src/hh/xhr.mjs` | все `data-qa`, тексты-маркеры (дословно из переводов hh) и адреса действий; чистые функции: InitialState, факты вакансии, прогноз, группы исходов, ответы hh на отклик, письмо и чат |
| сценарии | `src/flows/apply.mjs`, `net.mjs`, `recon.mjs`, `record.mjs`, `dom.mjs` | отклик (сухой прогон до кнопки или живой — 6.1b), сетевой журнал отклика, разведка, запись, общие действия со страницей |

**Предохранители.** `APPLY_LIVE=0` — робот не нажимает «Откликнуться» вообще; `POST /apply {dry: true}` (CLI) — сухой
прогон и при `APPLY_LIVE=1`. Сетевой фильтр рвёт не-GET запросы к `/applicant/…`, `/shards/applicant/…`, `chatik.hh.ru`
и переход на `?forceQuickResponse=true`. Выключается целиком только на время записи (откликается человек); живой отклик
открывает его по одному действию (`respond`, `quick`, `letter`, `chat` — `selectors.mjs` → `GUARD_ALLOW`), всё прочее
рвётся и при живом отклике. Потолок `APPLIER_DAILY_CAP=40` живых откликов в «день» робота (сверх — 429); 3 живых сбоя
подряд — блок `errors`.

**Окружение.** Сервис `applier` в `docker-compose.yml` (профиль `applier`): `init`, `shm_size: 1gb`, `mem_limit: 2g`,
`stop_grace_period: 200s`; порты `127.0.0.1:5901` (VNC; 5900 — «Общий экран» самого Mac) и `127.0.0.1:5682` (API для
CLI; 5681 занят брокером второго CLI n8n); том `applier_data:/data`; `./fixtures/applier:/data/recon` (не в git).
`.env`: `APPLIER_TOKEN`, `VNC_PASSWORD` (≤ 8 символов — ограничение VNC), `APPLY_LIVE`, `APPLIER_FAKE`,
`APPLIER_DAILY_CAP`, `HH_RESUME_TITLE`. Профиль браузера и сессия hh — только в томе; журналы — без текстов писем,
cookie и токена; разведка вырезает токены и данные аккаунта (`state.json`), а `page.html` хранит как есть — в
`fixtures/` (не в git).

### n8n (6.1–6.2)

- **W9 Robot** (`jobHunterW9Robot`): очередь в колонке `apply_state` ('' / queued / applying) — статусы прежние; операции

## 6.0: запуск, вход, разведка, запись

```bash
# 1. В .env: APPLIER_TOKEN (openssl rand -hex 24), VNC_PASSWORD (≤ 8 символов), APPLY_LIVE=0 — см. .env.example
scripts/deploy.sh --applier                      # профиль applier в COMPOSE_PROFILES, сборка и запуск робота
node scripts/applier.mjs status                  # браузер up, не вошли

# 2. Вход: откроется «Общий экран» (vnc://localhost:5901, пароль — VNC_PASSWORD) со страницей входа hh.
#    Войти по телефону и коду; закрыть плашки «Ваш регион — …?» и cookie. Команда ждёт входа до 10 минут
node scripts/applier.mjs login
docker compose restart applier && node scripts/applier.mjs status   # вход пережил перезапуск

# 3. Разведка: ~10 вакансий разных типов, 20–40 с между ними, без кликов → fixtures/applier/recon-…
node scripts/applier.mjs recon <id> <id> …
node scripts/applier.mjs recon --inbox           # «Отклики» и чаты; непрочитанные до и после должны совпасть

# 4. Запись: пользователь сам откликается в окне робота на 2–3 вакансии из ✅, робот снимает каждый экран и ответы hh
node scripts/applier.mjs record start
node scripts/applier.mjs record stop

# 5. Сухой прогон: до кнопки, без клика
node scripts/applier.mjs apply <id> --letter-file <файл>
```

Если робот упёрся в капчу или вышел из hh — блок (`status` покажет); после «Общего экрана» —
`node scripts/applier.mjs resume`.

### Разведка: что выяснили (10.10.2026)

**Вход.** Вошли через «Общий экран»; `hhtoken` живёт ~13 месяцев (до 11.2027), `hhrole`, `crypted_id`, `_xsrf` —
сессионные: робот восстанавливает их из бэкапа `storageState`, вход пережил `docker compose restart`.

**Прогноз без клика — `GET /applicant/vacancy_response/popup?vacancyId=N`** (его зовёт сам интерфейс hh):

| `type` | Что сделает hh по «Откликнуться» | Что в ответе |
|---|---|---|
| `modal` | окно с полем письма, отправка — кнопкой в окне | `responsePopup {type: normal}`, `responseStatus`, `relocationWarning`, `lastResponseLetter`, `lastResponseResumeHash` |
| `quickResponse` | отклик уходит сразу, письмо — «Приложить сопроводительное» после | `body {resume_hash, vacancy_id, letterRequired, letterMaxLength, responseStatus}` |
| `test-required` | переход на страницу вопросов работодателя | `redirect_uri`, `relocationWarning` |
| `alreadyApplied` | отклик уже есть | — |
| `need-login` | не вошли | `redirect_uri` на вход |

`relocationWarning.show` — покажет ли hh «Вы откликаетесь на вакансию в другой стране» (на Израиле и Москве — нет).
Без входа `popup` звать нельзя: hh, похоже, запоминает «откликнуться после входа» — у вакансии с тестом, которую
открывали до входа, после входа страница сама перешла на `/applicant/vacancy_response` (GET, ничего не отправляет;
предохранитель теперь такие переходы только пишет в журнал, рвёт лишь не-GET).

**Страница вакансии вошедшему:** `applicantVacancyResponseStatuses[id]` — `alreadyApplied`, `responseImpossible`,
`usedResumeIds` / `unusedResumeIds` (одно резюме), `test {hasTests, testId, required}`, `resumes`.
Из 5 вакансий в ✅ три оказались уже отправленными вручную без «📨 Отправил» — тот самый случай автоотметки 6.2.

**«Отклики»** (`/applicant/negotiations`, InitialState `applicantNegotiations`): по 20 на странице (136 всего, 7 страниц),
`applicantNegotiationsCounters` (всего: ждут ответа 77, отказ 49, собеседование 10). У отклика: `vacancyId`, `chatId`,
`lastState` (RESPONSE / DISCARD / INTERVIEW …), `viewedByOpponent`, `hasResponseLetter`, `hasNewMessages`, `lastModified`.
У 3 из 20 последних откликов `hasResponseLetter=false` — письмо до hh не дошло.

**Все «Отклики» листанием (20.10.2026, `docs/hh-applied.md`, `readNegotiations` в `applier/src/flows/recon.mjs`):**
пейджер — кнопки `data-qa="number-pages-N"` (выбранная — `number-pages-N number-pages-selected`) без ссылок, параметра

### Запись: как hh отправляет отклик (10.10.2026, 2 отклика пользователя в окне робота)

**Окно с письмом** (`modal`, вакансия с обязательным письмом): «Откликнуться» → `GET popup?vacancyId=N&isTest=…` →
окно (`vacancy-response-popup-form-letter-input`, `vacancy-response-submit-popup`) → письмо → «Откликнуться» в окне →
`POST /applicant/vacancy_response/popup` (multipart: `_xsrf`, `vacancy_id`, `resume_hash`, `ignore_postponed=true`,
`incomplete=false`, `mark_applicant_visible_in_vacancy_country=false`, `country_ids=[]`, `letter`, `lux=true`,
`withoutTest=no`) → ответ `{success: "true", topic_id, chat_id, responseStatus, …}` → вместо кнопки — «Чат»
(`vacancy-response-link-view-topic`). **Подтверждение отклика для робота — `success: "true"` в этом ответе.**

**В один клик** (`quickResponse`): клик по «Откликнуться» — это GET `/applicant/vacancy_response?vacancyId=…` →
**302 на `/vacancy/N?forceQuickResponse=true`** → страница сама шлёт `POST …/popup` (тот же ответ, письма нет, в форме
есть пустое `captchaText`) → «Резюме доставлено», «Приложить сопроводительное письмо», «Чат». Дальше «Приложить…» →
окно «Сопроводительное письмо» (`…letter-input`, «Отправить» `vacancy-response-letter-submit`) →
`POST /applicant/vacancy_response/edit_ajax` (`_xsrf`, `text`, `topicId`) — **у Nitka вернул 403
`{"error":"notEditable"}`**, письмо не прицепилось. Письмо дошло через чат: «Чат» → iframe
`chatik.hh.ru/chat/<id>?without_list=1` → у сообщения «Отклик на вакансию · Без сопроводительного письма» ссылка
«⊕ Добавить сопроводительное» (`chatik-chat-message-applicant-action`) → поле «Сопроводительное письмо»
(`chat-input-preview` + `text-input`) → «Отправить» (`chatik-do-send-message`) → `POST chatik.hh.ru/chatik/api/save
{text, messageId}` — `messageId` — само сообщение отклика: письмо встаёт в него («Отклик на вакансию · Здравствуйте!…»),
это не новое сообщение в переписке. Получилось даже при `writePossibility = DISABLED_BY_EMPLOYER` («Работодатель
отключил переписку») — больше писать в такой чат нельзя. Ответ `save` — общие настройки чата, успех — по коду 200.
Значит, запасной путь «письмо в чат» нужен на практике. Открытие чата шлёт `POST chatik/api/notify_chat_opened` —
поэтому входящие (6.2) читаем без открытия чатов.

**Окно отклика** держит предупреждения свёрнутыми: «Чтобы откликнуться… поменяйте видимость резюме»
(`hidden-resume-warning`, `max-height: 0`) есть в разметке окна, где отклик прошёл, и попадает в `innerText` — робот
считает его показанным только с высотой. hh подставляет в поле письма прошлое письмо (`lastResponseLetter`). Ответ на
отклик говорит, ушло ли письмо: `response_label` «…-with-letter» / «…-without-letter».

**Предохранитель:** в сухом прогоне и разведке рвём не-GET к `/applicant/…`, `/shards/applicant/…`, chatik и переход
на `?forceQuickResponse=true` (страница сама отправила бы отклик).

**Прочее.** `navigator.webdriver = true`; за 10 вакансий и «Отклики» капчи не было. У нового профиля всплывали
«Ваш регион — Москва?» и баннер cookie — закрыты при входе.

## 6.1a: W9 Robot — как устроено

```

   → Done → View (письмо «⏳ Робот откликается…» [⛔]) · Answer (тост) · Tick? → очередь
Очередь (tick: расписание раз в минуту, после 🚀, ▶️, капчи, смены ⚙️, сам W9 после успеха):
   Queue (apply_state не пуст) → Today (живые отклики робота с 09:00 по Таиланду) → Health (GET /health) → Gate
   Gate → Heal (applying > 6 мин → queued; не ✅ → снять) · Resolved (блок снят → «✅ снова в работе») ·
          Notice (капча — фото с ForceReply; вход / «Я не робот» / 3 сбоя / стоп hh — тревога с [▶️]; не отвечает, лимит — текст)
          · Gate views (нажали 🚀, а робот ждёт — «⏸ Робот ждёт: …») · Next → Claim (queued → applying) → Apply (POST /apply)
          → Result → View · Save result · Card: done · Shot (скриншот при сбое и сухом прогоне) · Panel sync (W7) · More → W9
⛔ (l:<id>:stop) → W9 stop: Unqueue (Update: id + apply_state=queued → '') → письмо с кнопками
▶️ (rb:go) / /go → W9 resume: POST /resume → тост или сообщение → очередь
Ответ на фото капчи → W3 → W9 captcha: POST /captcha → фото и ответ удаляются → «✅ Капча принята» → очередь | новое фото
⚙️ → 🚀 Робот: выключили → W9 dequeue (очередь назад в ✅, письма без 🚀); сняли паузу, сменили лимит → W9 tick
```

- **Очередь — колонка `apply_state`**, статус вакансии остаётся `approved` до отклика. Все переходы — Update с условием:
  двойное нажатие, ⛔ во время отправки и два параллельных W9 ничего не ломают (Update отдаёт только обновлённые строки).
- **Static data W9:** `alertedSince` (одна тревога на блок), `alertMessageId` (её поправить, когда блок снимут),
  `captchaPromptId`, `downDay` / `limitDay` (такие сообщения — раз в «день» робота). Импорт workflow её не стирает.
- **Тихие часы:** тревога, которую нашёл тик расписания (не нажатие), в 23–09 по Таиланду — без звука.
- **Письмо с 🚀** — W5 `Send letter: robot`, если `apply.enabled` и вакансия подходит (✅, письмо есть, нет теста, не на сайте
  работодателя); «↩️ Отменить» под «📨 Отправил» возвращает 🚀 так же. Старые письма — без 🚀 (решение пользователя).
- **Защиты W3:** пока вакансия в очереди, кнопки карточки, «📨 Отправил» и правка письма ответом не действуют.
- **Фейковый робот** (`APPLIER_FAKE=1` в `.env` → `scripts/deploy.sh --applier`): `node scripts/applier.mjs fake applied
  captcha login …` — следующие исходы по порядку (список — `fake help`); `/captcha ok` решает «капчу», ▶️ снимает блок.

- **CLI** `node scripts/applier.mjs apply` — всегда сухой прогон (`dry: true`): живой отклик только из W9, он ведёт таблицу.

  целиком. Первый прогон (11.10.2026) поймал две ошибки: `boundingBox()` ждал отсутствующий элемент 20 с на каждом

## 6.1c: автоотклик (20.10.2026)

**Зачем.** После сброса теневого режима (19.10) apply нейросети совпал с решением пользователя в 16 из 18 случаев (~89%,

| Тема | Решение пользователя |
|---|---|
| Что брать | ✅ пользователя и карточки с apply нейросети; вопросы работодателя и сайт работодателя — человеку |
| Окно на отмену | нет: письмо и отклик сразу (❌ на карточке, пока робот её не взял; ⛔ под письмом, пока в очереди) |
| Темп по умолчанию | «как руками»: пауза 20–60 с, ≤ 30 в час, ≤ 80 в день (⚙️ → 🚀 Робот: темп, лимит) |
| Часы | 09–23 по местному (тихие часы — ждёт); 🚀 работает и ночью |
| Хвост | карточки за 3 дня (`apply.backlog`), свежие первыми; панель показывает, сколько возьмёт |
| Письма | сначала — в ленту ответом на карточку, без звука; в тот же день (первый запуск) пользователь: «в чате спам — хочу просто открыть карточку автоотклик и видеть, что журнал пополняется» → письма автоотклика в чат не шлём (W5 «Quiet letter»: только запись), исход — в журнале панели, карточка правится на месте; письмо — в `/v<id>`. Письма к ✅ пользователя — в ленту, как раньше |
| Кнопка | «🤖 Автоотклик» под полем ввода открывает панель; ▶️ Запустить / ⏹ Остановить — в ней |
| Логгер | живая панель (состояние, день и час, следующий, очередь, журнал 8 попыток) + строка утренней сводки |

```

                               ▼                              ▼
W9 tick → Queue (пустая — пустой item) → Work? (очередь или автоотклик) → Today → Health → Gate
   Gate: … · limit · hour (health.pace.hour ≥ темп) · pace (health.pace.nextAt > сейчас) · night (в очереди только авто)
   └─ Auto on? (выше Next? — письма пишутся до отклика) → Auto rows → Feed (n8n/shared/auto.js → autoCandidates):
        ✅ с письмом, робот не пробовал       → Auto enqueue → W9 {op: enqueue, auto} → Plan → Enqueue (apply_mode = auto)
        waiting + apply, свежие первыми       → Auto claim (waiting → approved, letter_lock) → Write letter → W5 {auto}
        захват без письма > 10 мин (W5 упал) → Auto unclaim → waiting

      в работе (очередь + пишутся письма) — не больше 2

    в ленту → Save letter → Auto jobs (новое письмо при включённом автоотклике; «🔄» и правка — нет)
    не вышло (вызов от Feed) → Auto fail: waiting, apply_result = no_letter, apply_tries + 1; Feed — ещё раз через 15 мин, 2 раза
W9 Claim → POST /apply {…, pace: {min, max, hour}} → Result (apply_at) → More? → Pace wait (до pace.nextAt, ≤ 60 с) → Next tick
⛔ → apply_result = stopped (автоотклик её больше не возьмёт; 🚀 — возьмёт)
🤖 ▶️ (au:on) → apply.auto, apply.auto_since, apply.enabled = true, apply.paused = false → W9 tick
🤖 ⏹ (au:off) → apply.auto = false → W9 autostop: queued + apply_mode = auto → '' (stopped), письма снова с 🚀
```

**Темп держит робот** (`applier/src/pace.mjs`, состояние в `/data/state.json`): после каждой живой попытки — пауза
случайной длины в `[min, max]` из тела запроса (не меньше `APPLIER_MIN_GAP=15` с), откликов за час — не больше
`min(hour, APPLIER_HOURLY_CAP=40)`; рано → 429 `{reason: gap, retryAt}`, час исчерпан → 429 `{reason: hour}`, потолок
дня (`APPLIER_DAILY_CAP=100`) → 429 `{reason: day}`. Почему в роботе, а не в static data W9: запусков W9 бывает два сразу
(расписание + вызов себя), а static data не атомарна (урок PR #47). `/health` → `pace {nextAt, hour, hourCap, minGap}`;
по нему Gate не зовёт робота зря, панель показывает «следующий — не раньше …». Сухой прогон темп не трогает.

**Колонки** (`n8n/schema.mjs`, `migrate`): `apply_mode` ('' — 🚀, auto — автоотклик), `apply_at` — когда робот закончил
попытку (журнал панели, строка W6). Новых статусов и таблиц нет: вкладки, карточки и фильтры по статусу не менялись.
Авто-строки не портят теневой режим: `my_decision` у них пустой (карточка показывает «🤖 Автоотклик»).

**Журнал** — последние попытки робота по `apply_at` (`autoJournal`): `14:32 🤖🚀✉️ Senior Frontend — Ромашка /v123`,
`🧩 … · вопросы работодателя — сам`, `⛔ … · убрал из очереди`, `✉️ … · письмо не вышло`. Технический след каждого
отклика — журнал робота (`docker compose logs applier`, `/data/logs/*.jsonl`) с `requestId` = `<id строки>-<время>`.

**Безопасность.** Любой блок робота (капча, вход, 3 сбоя подряд, лимит hh, «нарушает правила») останавливает и отклики,
и подачу; при включённом автоотклике тревога о блоке приходит и при пустой очереди. `APPLY_LIVE=0` → автоотклик делает
только сухие прогоны (`dry_run` — такую вакансию он больше не берёт). Повтор после сбоя — только по 🚀.
Без сообщения с письмом W9 не правит письмо и не шлёт скриншот сбоя; «⏸ Лимит робота на сегодня» при автоотклике тоже не
приходит — лимит видно на панели. Сообщения в чат от автоотклика — только тревоги, где нужен человек (капча, вход, сбои).

(`pace.test.mjs`), `applier/sim/run.sh`. Живая проверка — на фейковом роботе и тестовых строках (хвост выключен, сбор на

## Несколько резюме: каким резюме откликается робот (16.10.2026, `docs/resumes.md`)

Бот передаёт в `POST /apply` поле `resume: { hash, title? }` — резюме вакансии (`vacancies.resume_id`), связанное с резюме на hh
(`resumes[].hh`, их создаёт импорт с hh). Без поля — как раньше: резюме по умолчанию, `HH_RESUME_TITLE` сверяет название.

Запись окна — разведка `node scripts/applier.mjs recon --chooser <id вакансии>` (16.10.2026, два резюме на hh; только вакансия,
где hh покажет окно, не «в один клик»; строгий предохранитель, ничего не выбирает и не отправляет; снимки — `fixtures/applier/chooser-…`):
- ячейка резюме в окне — `role="button"` вокруг `[data-qa="resume-title"]`; по нажатию открывается список
  `[role="listbox"][data-qa="magritte-select-option-list"]`, опции — `label[role="option"][data-qa="magritte-select-option-<хеш резюме>"]`
  (radio, `aria-selected`); название резюме в списке тоже `resume-title`, поэтому название окна берётся вне `listbox` (`SEL.resumeCurrent`);
- в списке — все резюме, и скрытое от работодателей (`accessType = no_one`); форма отклика шлёт `resume_hash` выбранного;
- страница вакансии заранее знает резюме: `applicantVacancyResponseStatuses[id].resumes[<id>]` — `_attributes.hash`, название,
  `accessType`; `usedResumeIds` — какими резюме уже откликались. С несколькими резюме hh показывает окно и там, где с одним
  был бы «один клик» (прогноз `modal`).

Сценарий (`applier/src/flows/apply.mjs`):
1. **До клика** (`resumeChoice` в `hh/state.mjs`): резюме нет среди резюме для отклика → `error`; этим резюме уже откликались → `already`;
   скрыто → `hidden` («открой его на hh»). Откликались другим — не мешает.
2. **Отклик в один клик** уходит сразу и резюме по умолчанию (`body.resume_hash` прогноза): если оно не то — `error` без клика.
3. **Окно:** название в окне уже то — список не открываем; иначе клик по ячейке → опция по хешу → название в окне сверяется
   с названием с hh (`pickResume`). Не вышло (нет ячейки, нет опции, не сменилось) — `error`, отклик не уходит.
4. **После отклика** страница вакансии перечитывается: `usedResumeIds` должен содержать выбранное резюме (`result.resume.used`),
   иначе в `warnings` — «hh не показывает резюме … среди использованных».
5. Сухой прогон (`apply <id> --letter-file f --resume <хеш>`) называет резюме и говорит, выберет ли его в окне.

n8n (W9): `Gate` кладёт в `next.resume` резюме вакансии, связанное с hh; основное без связи — без поля (как раньше); другое резюме без
связи — роботу нельзя: 🚀 не показывается (W5 «Format letter»), нажатие отвечает отказом (W9 «Plan»), из очереди такое снимает «Gate».

страницы, а слова «поменяйте видимость резюме» есть в окне всегда (свёрнутые) — получалось ложное `hidden`. Перед «текстовым»
экраном теперь перепроверяется окно (`SEL.modalSubmit`); симулятор ловил это плавающими падениями.
