# Установка для всех: профиль, онбординг, мастер

**Цель** (решение пользователя 13.10.2026): любой человек ставит себе свою копию системы одной командой, заходит в бота, присылает резюме PDF — и система ищет и оценивает вакансии под его профессию. Одна установка — один человек. Система владельца работает как раньше.

Решения пользователя (13.10.2026):
- любые профессии — поиск, фильтр и правила оценки выводятся из резюме;
- мастер установки `node scripts/install.mjs`, кнопки Telegram — через ngrok, как сейчас;
- после PDF — «Вот что я понял» и вопросы кнопками (подпись, контакт для HR, часовой пояс), потом сразу первый сбор;
- нейросеть — Gemini или Claude (из РФ не работают — об этом предупреждают README и мастер);
- образцы писем — по желанию; зарплата из резюме — правило для нейросети; теневой режим у новичка включён;
- проверка — чистая установка рядом с рабочей.

## Профиль в таблице `settings` (часть A)

Резюме, факты о человеке и его тексты лежат строками таблицы `settings` — той же, что у настроек бота (`docs/settings.md`). Все workflow уже читают её нодой «Settings», файлы `docs/resume.md` и `docs/letter-example.md` n8n больше не читает (монтирования `./docs` в контейнер нет). Строковая колонка Data Table — `TEXT` без лимита длины.

| Настройка | Что | По умолчанию | Кто читает |
|---|---|---|---|
| `profile.ready` | онбординг пройден | false | (часть D: W7, W8) |
| `profile.preset` | `generic` — правила из резюме · `frontend` — откалиброванные правила владельца в коде | `generic` | W2, W5 |
| `profile.resume` | текст резюме (≤ 30 000 знаков) | пусто | W2, W5 |
| `profile.extra` | «Дополнительно» — то, что человек дописал сам (свои проекты, фриланс); в промптах — разделом `## Дополнительно` | пусто | W2, W5 |
| `profile.facts` | факты из резюме, JSON: `name, first_name, name_gen, gender, position, position_gen, level, years, skills, companies, english, city, country, country_gen, citizenship, formats, salary, education, contacts` | `{}` | W2 (пресет frontend: `country_gen`), W5 |
| `profile.about` | строки «О кандидате» промпта W2 | `[]` | W2 |
| `profile.signature` | подпись письма | пусто | W5 |
| `profile.contact` | строка контакта в конце письма | пусто | W5 |
| `llm.rules` | правила оценки пресета generic: `{ skip, maybe, apply, ignore, notes }` — списки строк | `{}` | W2 |
| `letters.examples` | свои образцы писем (≤ 4000 знаков); пусто — блока примеров в промпте нет | пусто | W5 |
| `letters.prompt` | замена разделов промпта W5: `{ intro, facts, style }` | `{}` | W5 |

**Пол** (`facts.gender`: `m` / `f` / пусто) — только из резюме или ответа человека, по имени не угадываем: от него зависят глаголы письма от первого лица («делал» / «делала»). Пусто — нейтральные формулировки.

**Умолчания** — поведение до онбординга (у владельца это его текущие настройки). Онбординг записывает все свои строки явно, поэтому умолчания на нового человека не влияют.

### Пресеты

- **frontend** — у владельца. Промпт W2 — откалиброванные правила в коде (`FRONTEND_RULES` в `n8n/w2-score/build-prompt.js`): React/Vue, AI на JS/TS, встроенные спорные случаи (`BUILTIN_CASES`), подсказка к AI-вакансиям. Личное — из профиля: «О кандидате» (`profile.about`), страна для правила о ночных часах (`facts.country_gen`). W5 — разделы из `letters.prompt` (его строки), база фронтендера (`IMPLIED`) в разметке навыков, зачины «про стек».
- **generic** — у всех остальных. Промпт W2 — правила из резюме (`llm.rules`), спорные случаи (`llm.cases`) — просто дополнительные поправки. Промпт W5 собирается из фактов: «от имени {name_gen}, {position_gen}», компании из резюме, нейтральные зачины, «Дополнительно» — только если есть.

### Промпты

- **W2** (`n8n/w2-score/build-prompt.js`): шапка (кандидат-фронтендер / кандидат) → «О кандидате» → правила пресета → «Текст между <vacancy>…» → `reason` и поправки → резюме. `prompt_v` — хеш всего, что до резюме.
- **W5** (`n8n/w5-letter/build-letter.js`): вступление → «Факты» → «Как писать» + строка «Последние две строки: «контакт» и «подпись»» → «Нельзя» → примеры (если есть) → профиль.
- **W5 Parse letter**: если модель пропустила контакт или подпись — дописывает их. Контакт считается найденным по «ключу» строки контакта: `@ник`, e-mail или телефон.

### Перенос и бэкап

```bash
node scripts/n8n-api.mjs profile-export docs/profile.json   # все строки settings в JSON (права 600)
node scripts/n8n-api.mjs profile-import docs/profile.json   # JSON { "имя": значение } → upsert по name
```

- `docs/profile*.json` — в `.gitignore`: там резюме и контакты.
- Импорт проверяет значения схемой `n8n/shared/settings.js`: хоть одно не проходит — не пишется ничего. Имя, которого эта версия кода не знает, пишется с предупреждением — код пропускает его, пока не узнает.

**Перенос владельца** (13.10.2026). `docs/profile.json` собран из `docs/resume.md`, `docs/letter-example.md` и строк прежних промптов (пресет frontend). Импорт — до деплоя: старый код незнакомые имена пропускает.

Проверка «до символа»: старый код из `develop` против нового. На 40 живых вакансиях и настройках владельца совпали:

## Часовой пояс человека (часть B)

- **Источник** — настройка `profile.tz` (IANA, например `Asia/Bangkok`). Пусто — пояс компьютера `USER_TZ` из `.env` (его пишет мастер установки), иначе Москва. У владельца — `Asia/Bangkok`.
- **Код** — `n8n/shared/time.js`, подключается раньше `card.js` и `robot.js`. При подключении вычисляет `TZ`: строка `profile.tz` из ноды «Settings», если она есть в workflow, иначе `USER_TZ`. «Settings» есть во всех workflow, где показывается время, — с 13.10.2026 и в W3, W4 (`onError: continue`: без таблицы кнопки и тревоги работают).
- **Помощники:** `localHM`, `localDM`, `localDay`, `localHour`, `localDate`/`localTime` (из ISO), `localMsk` («14:32 (10:32 МСК)»; у москвича — «10:32 МСК»), `tzLabel`, `localDayStart`, `quietHours`.
- **Что по местному:**
  - время в карточках, меню, статистике, сообщении о сборе;
  - тревоги W4 и «снова работает»;
  - тихие часы 23–09;
  - «день» робота с 09:00 (W9 «Today» берёт отклики за двое суток, «Gate» считает день через `robotToday`);
  - утренняя сводка в 10:00.
- **Что по Москве:** расписание сбора (`collect.*`, hh публикует по МСК). В ⚙️ → 🕐 Сбор рядом — местные часы.
- **Сводка W6** — её запускают «часы» W8 (нода «Summary due»): местное время ≥ 10:00 и сводки за сегодня ещё не было (static data `summaryDay`). Mac спал в 10:00 — сводка уйдёт на первом тике после пробуждения. Первый тик после деплоя только запоминает день: если уже позже 10:00, сегодняшнюю сводку прислал прежний cron. У W6 больше нет своего расписания, его вызывает W8, поэтому публикуется он вместе с W8 (не при `--paused`).
- **Робот** (`applier`): браузер, «день» для `APPLIER_DAILY_CAP` и окно обслуживания (05:00–06:00) — по `USER_TZ` компьютера. После смены `USER_TZ` — `scripts/deploy.sh --applier`.

Проверка (13.10.2026) — старый код против нового при одном «сейчас» на живых данных владельца:
- панели W7 (статистика, список, ⚙️, 🕐 Сбор, 🚀 Робот), тревоги W4 и «снова работает» совпали;
- отличаются только подписи: «по Таиланду» → «по местному», в статистике — время с МСК в скобках;
- `npm test` робота: «день» с 09:00 для Бангкока, Москвы и Нью-Йорка.

## Поиск и фильтр под любую профессию (часть C)

**Параметры поиска** — из настроек и профиля (`n8n/shared/search.js`, `docs/settings.md`):
- слова: `search.anywhere` (по всему тексту, может быть пусто) и `search.in_name` (`NAME:(…)`);
- роли hh: `search.roles` → `professional_role`; справочник — `n8n/shared/hh-roles.js` (27 групп, 194 роли). Пересобрать: `node scripts/hh-roles.mjs <сохранённая страница поиска hh>`;
- формат работы `search.formats`, город `search.area` (`{ id, name }`, регион hh), образование `search.education`, период `search.period`.

**Запросы сбора** (`searchQueries`). hh не умеет «удалёнка везде ИЛИ офис в городе» одним запросом, поэтому их до двух:
- «удалёнка» — `work_format=REMOTE`, без региона;
- «офис и гибрид, {город}» — остальные форматы + `area`. Без города офис не ищется: по всем регионам это тысячи вакансий.

Нет ни одного запроса — W1 «Plan» падает с понятной ошибкой (тревога W4). У владельца — один запрос, URL прежний до символа. Проверено на живом hh 13.10.2026: бухгалтер, офис и гибрид, Казань — 44 вакансии за сутки (`fixtures/search-office-kazan.html`, не в git).

**W1:**
- «Plan» отдаёт готовый `url` на каждый запрос, «Search hh» берёт его как есть;
- бэкфилла больше нет: первый сбор нового человека сразу идёт в оценку (поиск ограничен периодом). Нода «Any row» удалена;
- «Parse search»: пустая выдача — норма, если hh сказал «найдено 0» (узкая профессия в одном городе); поломка — только если вакансии есть, а разобрать их не вышло;
- сообщение о сборе: найдено по каждому запросу («удалёнка 37 + офис и гибрид, Казань 12») и ссылка на каждый.

**Фильтр.** Правила фронтенда (`FRONTEND_FILTER_RULES`: Angular, «чужой стек», «бэкенд», «нет React и Vue» вместе с «AI не на JS/TS») работают только у пресета `frontend`. У `generic` их нет и в ⚙️ → 🧹 → Правила (своя раскладка на 6 кнопок). `lead` у `generic` по умолчанию выключен — его выключает онбординг: «руководитель» и «архитектор» — это и есть профессии.

**W2, текст вакансии у `generic`:**
- если в профиле есть желаемая зарплата — строка «Зарплата: от … до … ₽ на руки» (или «не указана»);
- если человек ищет офис или гибрид — подпись города «для офиса и гибрида — город работы».

У пресета `frontend` текст прежний.

**Проверка:**
- у владельца: URL поиска и решения фильтра на 250 вакансиях — как раньше; промпты W2 и W5 — до символа (`prompt_v` `chqob3`);
- у `generic`: фронтенд-правила не срабатывают; «Plan» для «удалёнка + офис, Казань» даёт два запроса; пустая выдача («найдено 0») проходит без тревоги.
