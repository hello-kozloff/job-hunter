## 1. Цель

Система в n8n, которая:
1. сама мониторит вакансии (сначала hh.ru, потом другие сайты);
2. отбирает по правилам пользователя;
3. пишет сопроводительное письмо (LLM);
4. откликается, включая случаи с внешней веб-формой.

## 4. Выбранный метод — разбор

Две разные задачи.

### Чтение: поиск + страница вакансии

Публичные страницы, вход не нужен, аккаунт не рискует. Риск: капча/блок по IP.

Проверено 06.10.2026. Фикстуры лежат в `fixtures/`, в git не входят.

**Поиск `/search/vacancy`:**
- `<template id="HH-Lux-InitialState">` — JSON состояния страницы **с HTML-сущностями** (`&#34;` и т. п.). Раскодировать за один проход, потом `JSON.parse`.
- `vacancySearchResult.vacancies` — все 100 вакансий страницы; `totalResults` — сколько всего.
- Поля вакансии: `vacancyId`, `name`, `company{id,visibleName}`, `compensation{from,to,currencyCode,gross}` или `noCompensation`, `publicationTime.$`, `creationTime`, `workExperience`, `employmentForm`, `workFormats[].workFormatsElement`, `languages[].language[{isoCode,degree}]`, `userTestPresent`, `@responseLetterRequired`, `totalResponsesCount`, `snippet{req,resp,cond,skill}` (с `enable_snippets=true`), `area.name`.
- В HTML-разметке только ~20 карточек из 100 → **селекторы `data-qa` не используем**.
- `page=1` работает.

**Страница вакансии `/vacancy/<id>`:**
- JSON-LD `JobPosting`: title, description (HTML), datePosted, validThrough, hiringOrganization.name, jobLocation. **Зарплаты нет.**
- InitialState → `vacancyView.vacancyFull.vacancy`: `description` (HTML), `keySkills[]`, `workExperience`, `employmentForm`, `workFormats[]`, `compensation`, `languages`, `status.archived`, `area.countryIsoCode`, `acceptLaborContract`, `civilLawContracts`.
- `applicantVacancyResponseStatuses[<id>]`: `test{hasTests,testId,required}`, `letterMaxLength`.
- Признак внешнего отклика (аналог `response_url` из API) на сайте пока не найден — проверить на этапе 2.

### Отклик

Требует аккаунта.

| Путь | Суть | Решение |

## 5. Поисковый запрос

Рабочий запрос (W0, W1; источник правды — `n8n/shared/search.js`, его же показывает сообщение о сборе), с 07.10.2026:

```
https://hh.ru/search/vacancy?text=frontend OR NAME:(react OR next.js OR nextjs OR vue OR vue.js OR vuejs OR nuxt OR nuxt.js OR nuxtjs OR typescript OR AI OR ИИ OR LLM OR GenAI OR GPT OR нейросети OR нейросетей)&professional_role=96&work_format=REMOTE&education=not_required_or_not_specified&search_period=1&order_by=publication_time&items_on_page=100&enable_snippets=true&ored_clusters=true&page=0
```

- `frontend` — по всему тексту вакансии (название, описание, навыки): находит «JavaScript-разработчик», fullstack и AI-вакансии с фронтендом в описании. Синонимы (Frontend ↔ Фронтенд, front-end) hh подставляет сам.
- `NAME:(…)` — язык запросов hh: искать только в названии. Стек и AI — только в названии: по всему тексту они приносят чужой бэкенд («React будет плюсом»).
- `search_period=1` — только за сутки (решение пользователя 07.10.2026). `ored_clusters=true` — как в выдаче на сайте, с одиночными фильтрами на результат не влияет.
- `professional_role=96` — «Программист, разработчик». AI-инженеры из роли «Дата-сайентист» — это ML, их не берём (решение пользователя 07.10.2026).
- `education=not_required_or_not_specified` важен: у пользователя среднее образование.
- Регионы — все (параметра `area` нет): РФ, Казахстан, Узбекистан, Беларусь, Грузия, Сербия, Израиль…
- Замер 07.10.2026 за сутки: прежний запрос (всё в названии) — 16 вакансий; `frontend` по всему тексту — 34; текущий — 39, из них фильтр по названию пропускает 16. Выдача за сутки умещается на одной странице (100).
- Шум в выдаче: чужой бэкенд (Ruby on Rails, C#/.NET, DWH, Java), React Native, Angular. Его режет фильтр этапа 2 (§7).
- Старые варианты:
  - `NAME:(frontend OR front-end OR фронтенд OR react OR … nuxtjs)` без `search_period` (06–07.10.2026): только названия, за всё время (161 вакансия, 2 страницы); терял вакансии без этих слов в названии;
  - `text=Frontend` по всему тексту за всё время: 531 вакансия, по делу ~15%. За сутки и со стоп-словами по названию — то, что используется сейчас;
  - `text=Frontend&search_field=name`: 99 вакансий, теряет «React-разработчик».

## 6. Архитектура

```
[W0 Check hh]  ручная проверка «жив ли hh» (этап 0)
[W8 Clock]     Schedule каждые 15 мин → Settings → Due (слот по расписанию из настроек бота прошёл с прошлой отправки?
                 static data dispatchedAt; после сна — один догоняющий) → W1. По умолчанию, МСК: днём 07:00–17:30 каждые
                 30 мин, ночью 18, 20, 22, 00, 02, 04, 06 — 29 в сутки (docs/settings.md)
[W1 Collector] вызов из W8 (kind schedule | catchup) или W7 «🔄 Собрать сейчас» (kind bot) | Manual
                 → Busy + Start: журнал runs (идёт другой сбор — запись running моложе 10 мин — этот пропускаем)
                 → Start run (запись running) → поиск hh → разбор InitialState → склейка дублей
                 → только новые (нет ни external_id, ни dup_key) → Blacklist + Filter search (правила по выдаче)
                 → Insert (new | rejected) → для new: страница вакансии → Parse vacancy (правила по описанию)
                 → Update (detailed | rejected) → Score job (блок «🔎 Сбор»: запросы к hh, что искали, новые и отсеянные
                 с причинами, следующий сбор) → Finish run (итог в runs) → W2 (Execute Workflow, без ожидания);
                 поломка → Fail run (status error) → Stop. Успешные запуски W1 не хранятся (итог — в runs)
[W2 Score]     вызов из W1 после каждого сбора | Manual → detailed → Claim (detailed → scoring одним UPDATE: второй запуск W2
                 те же строки не возьмёт) → резюме + промпт → Gemini | Claude → apply/maybe/skip + причина
                 → карточка в Telegram с кнопками ✅/🤔/❌ → status = waiting → сообщение о сборе + тревоги (429 и т. п.):
                 были карточки — «🔎 Сбор» сверху итога «📊 Оценено N»; нет — «🔎 Сбор» одним живым сообщением без звука
                 (прошлое удаляется, static data W2 `liveId`; решение пользователя 07.10.2026); число карточек → runs
[W3 Telegram]  Telegram Trigger (вебхук через ngrok) → кнопка: my_decision, status, перерисовать карточку,
                 при расхождении с нейросетью «Почему?» → ответ (reply) → my_reason; отсеянная фильтром — решение с панели
                 (/v<id>: страница с hh, если нет описания → новая карточка в ленте → «Почему?» → письмо; «🤖 На оценку» → W2);
                 меню бота (кнопки под полем ввода, /v<id>, кнопки панели, ⚙️ Настройки) → W7
[W5 Letter]    вызов из W3 (✅ / «🔄 Переписать» / ответ на письмо; W3 сначала ставит letter_lock — UPDATE «где пусто»,
                 повторное нажатие письмо не запускает; W5 снимает блокировку в конце, зависшую — W3 через 3 мин)
                 | Manual → профиль + образец → Gemini | Claude
                 → письмо ответом на карточку: [📝 Отклик на hh] [🔗 Вакансия] [🔄 Переписать] [📨 Отправил]
                 → прежнее письмо (и ответ с пожеланием) удаляется; после «📨 Отправил» — [↩️ Отменить] [📋 К вакансиям]
[W4 Errors]    Error Trigger → Format error (ключ: workflow + нода + текст без чисел и ссылок) → Find alert (открытая в alerts)
                 → новая: тревога со звуком + запись в alerts; повтор в течение 6 ч: правка той же тревоги без звука
                 «🔁 ×N, с … до …» (07.10.2026). Успешный W1 / W2 закрывает свои тревоги: «✅ снова работает»
[W6 Summary]   06:00 МСК (10:00 Таиланд): «⌛ устарела» (3 дня без решения), хвосты → проверка на hh «🔒 закрыта»,
                 сводка: воронка, хвосты, теневой режим, сбои (сборы — по runs, ошибки — публичный API n8n, туннель);
                 без звука, если сбоев нет; чистка: описания отработанных вакансий старше 30 дней, runs старше 90 дней
[W7 Bot menu]  вызов из W3 | Manual (приветствие с кнопками) → вся таблица + журнал runs → панель: список по вкладкам
                 (8 на странице, /v<id> — карточка с решением), статистика, ⚙️ настройки (сбор: интервалы, «день»,
                 пауза, «собрать сейчас»; смена расписания → API healthchecks); одна живая панель (docs/bot-menu.md)
[Страж]        healthchecks.io (OnCalendar = расписание сбора, grace = интервал днём + 20 мин; бот обновляет его через API
                 при смене расписания): W1 шлёт сигнал после поиска; нет сигнала → их бот пишет в Telegram
```

**Статусы:** `seen` (бэкфилл, не обрабатывается) | `new` (прошла выдачу) → `detailed` (прошла все правила; если `error` — страница не открылась, оценка по фрагменту) | `rejected` (+ `reasons`) → `scoring` (W2 оценивает; карточка не ушла — «Release» вернёт в `detailed`, застрявшие дольше 30 мин вернёт W6) → `waiting` (W2: решение нейросети, карточка отправлена) → `approved` (✅) | `maybe` (🤔) | `skipped` (❌); `approved` + письмо (W5) → «📨 Отправил» → `applied` (+ `applied_at`); W6: `waiting` 3 дня → `expired`, закрыта на hh → `archived`; этап 6+: `failed | needs_human`.

**Хранилище:** n8n Data Tables, таблица `vacancies`.
- Лимит поднят до 100 МБ env-переменной.
- Уникальность по `external_id`.
- Одна вакансия в разных регионах — это разные id. Склеиваем по `dup_key = hh:<company_id>:<нормализованное название>`; у скрытой компании — `hh:id:<id>`. Регионы копий собираются в `areas`.

**Схема `vacancies`:**
- источник правды — `n8n/schema.mjs`; новая колонка → `node scripts/n8n-api.mjs migrate`;
- этап 1: `source, external_id, dup_key, title, company, company_id, areas, salary_from, salary_to, currency, salary_gross, experience, employment_form, work_formats, languages, key_skills, has_test, letter_required, responses, snippet, url, apply_url, apply_type (hh|external|manual), published_at, status`;
- этап 2: `contract` (tk,self_employed,individual_entrepreneur,individual_person), `reasons`, `description` (текст ≤ 8000), `error`;
- этап 3: `decision` (apply|maybe|skip|error), `llm_reason`, `llm_model`, `my_decision` (кнопка: apply|maybe|skip|earlier), `my_reason` (ответ на «Почему?»), `tg_message_id` (карточка), `tg_ask_id` (вопрос «Почему?»);
- этап 4: `letter`, `tg_letter_id` (сообщение с письмом — на него отвечают с правкой), `letter_notes` (пожелания к письмам через « | »), `applied_at`;
- этап 5: `card_at` (когда W2 отправил карточку — от него считаются 3 дня);
- 07.10.2026: `letter_lock` (защита от двойного ✅), `prompt_v` (версия промпта оценки: хеш правил без резюме — по нему теневой режим разбирается по версиям);
- таблица `blacklist`: `company, comment`;
- таблица `runs` — журнал сборов W1: `started_at, finished_at, kind` (schedule | catchup | bot | manual), `status` (running | ok | error), `found, uniq, fresh, rejected, scoring, pages, cards, error`;
- таблица `settings` — настройки из бота: `name, value_json` (только изменения; значения по умолчанию — в коде);
- таблица `alerts` — тревоги W4: `alert_key, workflow, message, first_at, last_at, hits, is_open, tg_message_id`;
- имена колонок обходят служебные слова SQL (key, value, trigger, count, unique, open);
- `id, createdAt, updatedAt` — встроенные.

**Telegram:**
- свой бот (токен в Credentials), один личный чат для всего;
- chat_id — в `.env` как `TG_CHAT_ID`, в нодах `{{ $env.TG_CHAT_ID }}` (Variables в Community edition нет);
- кнопки ловит W3 через Telegram Trigger (v1.5: проверяет секретный заголовок, Restrict to Chat IDs = TG_CHAT_ID). Публичный HTTPS → контейнер ngrok (`COMPOSE_PROFILES=tunnel`, `ngrok/policy.yml`), `WEBHOOK_URL=https://<NGROK_DOMAIN>/` (→ `N8N_WEBHOOK_URL`);
- callback_data кнопок: `v:<id строки>:<apply|maybe|skip|earlier|ban|edit>` — карточка (`ban` — «🚫 В ЧС»: компания в `blacklist`, вакансия — ❌ с причиной «чёрный список») (`earlier` — «📨 Уже откликался», 07.10.2026: status = applied без письма и `applied_at`, без «Почему?», вне теневого режима); `l:<id>:<redo|sent|unsent>` — письмо; панель меню (W7): `p:l:<tab>:<page>`, `p:s`, `p:x`, `p:n` («📋 К вакансиям» под отправленным письмом), `pv:<id>:<choice>:<tab>:<page>` (`score` — «🤖 На оценку» у отсеянной фильтром, 08.10.2026);
- меню бота (07.10.2026, `docs/bot-menu.md`): кнопки под полем ввода `[📋 Вакансии] [📊 Статистика]` (ставит `/start`), одна живая панель — нажатие пользователя и прошлая панель удаляются, листание правит панель на месте;
- тихие часы: 23:00–09:00 по Таиланду — карточки и сводка без звука (`disable_notification`), тревоги со звуком;
- не использовать «Send and wait» на каждую вакансию.

**Особенности n8n 2.x (проверено на 2.42.3):**
- «Publish» вместо «Activate»; импорт workflow через CLI снимает публикацию со всех → `deploy.sh` после импорта публикует рабочие заново (W1, W2, W4, W5, W6; W3 — при туннеле; `--paused` — без W1/W2/W6); CLI-публикацию запущенный n8n видит только после перезапуска (`deploy.sh` перезапускает сам);
- **Error workflow (W4) должен быть опубликован** — иначе в логе «Workflow … is not active and cannot be executed» (документация n8n утверждает обратное — неверно для 2.42);
- **дочерний workflow (Execute Workflow) тоже должен быть опубликован**, если его вызывает опубликованный: иначе та же ошибка в ноде вызова (W3 → W5, 07.10.2026) → `deploy.sh` всегда публикует W5, а W2 (его вызывает W1) — вместе с W1;
- Code-ноды работают в task runner: без `require` и `process.env`;
- Error workflow не срабатывает на ручных запусках;
- HTTP Request (Response Format = Text + Include Response Headers and Status) кладёт тело в поле **`data`**, не `body`;
- CLI `n8n execute` не грузит модули → Data Table в нём не работает («module is disabled»). Workflow с таблицами запускать через REST `POST /rest/workflows/:id/run` (`scripts/n8n-api.mjs run`); второй CLI-процесс — с `N8N_RUNNERS_BROKER_PORT=5681`;
- Telegram-нода без `parse_mode` шлёт Markdown (символ `_` ломает отправку) → всегда `parse_mode: HTML` + экранирование;
- Data Table: таблицу можно указать по имени (`mode: name`), Insert «Map Automatically» пишет все поля item → поля должны совпадать с колонками;
- Cron у Schedule Trigger зашит в workflow — из таблицы его не прочитать. Расписание из настроек бота → «часы» W8 Clock тикают каждые 15 мин и сами решают, пора ли собирать (07.10.2026);
- Schedule Trigger 1.4: `misfirePolicy: coalesce` — после сна Mac выполняется последний пропущенный запуск, но **на каждое правило (rule)**; `coalesce_owner` — один на всю ноду. У W1 два правила (день/ночь) → `coalesce_owner`, иначе сон через 18:00 дал бы два параллельных W1 и дубли (проверено по исходникам 2.42.3: `@n8n/scheduler` → `coalesce-group.js`). Деплой сразу после пробуждения пересоздаёт задания — догоняющий запуск теряется;
- `import:credentials` принимает данные открытым текстом и сам шифрует их ключом из `.env`;
- вход в REST ограничен по частоте (429 после нескольких логинов подряд) → `n8n-api.mjs` хранит cookie сессии в `.n8n-session` (права 600, не в git);
- REST `/executions?filter=`: `status` — только массив (`["success"]`), строка → 400;
- Data Table Insert/Update «Map Automatically» отправляет все поля item, кроме id/createdAt/updatedAt → лишние поля ломают запись. Нужно несколько колонок — `defineBelow` (`setColumns()` в build-workflows.mjs);
- Data Table Get умеет сортировку и по системным колонкам (`createdAt`, `updatedAt`);
- Telegram-нода возвращает `{ ok, result: { message_id } }`; с `onError: continueRegularOutput` ошибка отправки — item `{ error }`;
- HTTP Request с credential: `authentication: predefinedCredentialType` + `nodeCredentialType` (`googlePalmApi` кладёт ключ в `?key=`, `anthropicApi` — в `x-api-key`);
- `N8N_WEBHOOK_URL` — актуальное имя (просто `WEBHOOK_URL` в 2.42 устарел);
- execution order v1: ветки одной ноды выполняются по очереди сверху вниз (каждая целиком) — так W2 шлёт сводку после карточек, а W1 вызывает W2 после ветки вакансий.
- Telegram-нода: число inline-кнопок задаётся при сборке (fixedCollection), выражениями — только подписи и callback_data; неизвестные ключи collection (`is_persistent`, `reply_markup` в Additional Fields) n8n отбрасывает при выполнении (`getNodeParameters`). Telegram-credential нельзя использовать в HTTP Request (токен — в пути URL) → меню W7 на фиксированных раскладках, вакансия открывается командой `/v<id>` в тексте;
- Telegram: сообщение с ForceReply («Почему?») прячет reply keyboard меню, и сама она не возвращается — нужна новая отправка `ReplyKeyboardMarkup` → в `build-workflows.mjs` `MENU_KEYBOARD` у простых сообщений (W3 «Confirm», W2 и W6 «Send summary», W7 приветствие); inline-кнопки сообщения её не несут (одна разметка на сообщение);
- Data Table Update возвращает только обновлённые строки: ни одна не подошла под условие — выход пустой. На этом строятся атомарные «захваты» (UPDATE с условием вместо «прочитать → проверить → записать»); Delete — операция `deleteRows`; условия фильтра: eq, neq, like, ilike, gt, gte, lt, lte, isEmpty, isNotEmpty, isTrue, isFalse;
- `$getWorkflowStaticData` работает в Code-ноде (task runner возвращает изменения) и сохраняется у запусков не из редактора, в том числе integrated (дочерний workflow); Data Table Get не умеет skip — для страниц брать всю таблицу или публичный API `/api/v1/data-tables/{id}/rows` (limit + cursor);

**ngrok (бесплатный тариф, проверено 07.10.2026):** действие `restrict-ips` платное (`ERR_NGROK_2263`, туннель не стартует) → то же через выражение `inCidrRanges(conn.client_ip, [...])` + `custom-response`; домен вида `*.ngrok-free.dev`; `--url` вместо устаревшего `--domain`; токен — `NGROK_AUTHTOKEN` в environment контейнера. Проверка снаружи: любой адрес не с IP Telegram → 403.

## 8. Проблемы и решения

1. **Блок/капча.**
   - Профилактика: браузерные заголовки, редкие запросы (29 в день по одной странице: днём раз в 30 мин, ночью раз в 2 ч).
   - Детектор блока срабатывает, если: статус ≠ 200 (по редиректам не идём — 3xx виден), нет `HH-Lux-InitialState`, JSON не разбирается, 0 вакансий, у вакансий нет id/name.
   - Реакция: HTML в `fixtures/` → Stop and Error → тревога из W4.
   - **Слово «captcha» встречается и на нормальных страницах** — по нему одному не детектить.
   - Если блок постоянный → другой IP или письма автопоиска.
2. **Сломалась вёрстка** → тот же детектор. Сохранённый HTML — фикстура для `scripts/run-code-node.mjs`. Источники данных — InitialState и JSON-LD, не data-qa.
3. **Дубли и пропуски.**
   - Дедуп по `external_id` + `dup_key`: одна вакансия в 8 регионах = 8 id (пример: Nitka).
   - Выдача отсортирована по дате публикации; поднятые вакансии отсекаются по id.
   - выдача за сутки (~40 вакансий) умещается на одной странице (100) и с запасом покрывает ночной интервал в 2 часа.
4. **Mac спит или выключен** → запуски пропускаются, но следующий забирает всё за сутки (`search_period=1`) — простой до суток без потерь, дольше — вакансии старше суток не соберутся; после пробуждения — один догоняющий сбор. Docker Desktop стартует при входе в систему, у контейнера `restart: unless-stopped`. На батарее с закрытой крышкой Mac спит (`pmset -g log`, 07.10.2026: сон до 14:53 по Таиланду — пропущены сводка и сбор) → ночные сборы идут, только если Mac открыт, на зарядке и сон при выключенном дисплее запрещён (Настройки → Аккумулятор → Параметры).
5. **Плохая LLM-оценка** → строгий JSON `{score, decision, reasons, red_flags}` (Structured Output Parser); неделя теневого режима; в промпте: текст вакансии — данные, не инструкции.
6. **Плохое письмо** → только факты из `docs/resume.md`, запрет выдумывать; 2–3 связки «требование → реальный опыт»; коротко; проверка пользователем.
7. **Тест / вопросы / внешний сайт** → `needs_human`, ссылка в Telegram.
8. **Риск аккаунта (этап C)** → свой дневной лимит 15–30 откликов, случайные паузы, рабочие часы, `DRY_RUN` (дойти до кнопки, скриншот, не жать), капчу не обходить — отдавать человеку.
9. **Секреты.**
   - Токены и ключи в n8n — в Credentials (шифруются `N8N_ENCRYPTION_KEY`).
   - `.env` (ключ шифрования, chat_id, токен бота, логин/пароль владельца n8n) — права 600, в `.gitignore`; токен бота попадает в n8n через pipe (`deploy.sh`), на диск хоста кроме `.env` не пишется.
   - `docs/resume.md` — в `.gitignore`.
   - Фикстуры hh тоже не в git: в JSON есть имена HR-менеджеров.
10. **Другие сайты** → свой сборщик на каждый, выход в единую схему (п. 6).
11. **Размер страниц** → страница поиска весит ~1,7 МБ, поэтому история запусков хранится 7 дней (`EXECUTIONS_DATA_MAX_AGE=168`). 07.10.2026 база n8n выросла за день с 66 до 122 МБ → успешные запуски W1 больше не хранятся (итог сбора — в таблице `runs`), `DB_SQLITE_VACUUM_ON_STARTUP` сжимает базу при каждом перезапуске (деплой). Таблицы (лимит 100 МБ): W6 каждое утро убирает описания отработанных вакансий старше 30 дней и записи `runs` старше 90 дней.

## 11. Справка: API hh (на случай, если появится токен)

Изучено по официальной документации (api.hh.ru/openapi/redoc):
- `GET /vacancies`: без токена капча после первого запроса (403); заголовок `HH-User-Agent` обязателен; неизвестные параметры молча игнорируются; глубина выдачи ≤ 2000; `per_page` ≤ 100.
- Полезные параметры: `search_field` (несколько, по умолчанию все поля), `experience` (несколько), `work_format`, `education`, `date_from` (ISO, нельзя вместе с `period`, округление до 5 мин — для инкрементального сбора), `excluded_text` (слова через запятую), `label` (`not_from_agency`, `with_salary`), `responses_count_enabled=true` (поле `counters.responses`), `no_magic=true`.
- Устарели: `schedule`, `employment`, `only_with_salary`, `part_time`, `premium`.
- `GET /vacancies/{id}`: полезные поля — `description`, `key_skills`, `experience`, `salary_range`, `work_format`, `response_letter_required`, `has_test`, `test.required`, `response_url` (не null = отклик на внешнем сайте), `apply_alternate_url`, `archived`, `closed_for_applicants`, `languages`, `internship`.

## 14. Git

Решения пользователя (07.10.2026), подробно — `docs/git-flow.md`.

- **Коммиты, PR и имена веток — только по-английски.** Формат — Conventional Commits: `feat(w1): collect every 30 min by day`. Типы: feat, fix, docs, refactor, perf, test, build, chore, revert. Scope — `w0`…`w6`, `shared`, `schema`, `deploy`, `scripts`, `stage-N`. Нужен ручной шаг после деплоя (migrate, `.env`, действие пользователя) — `!` и `BREAKING CHANGE:`.
- **Ветки:**
  - `production` — проверенное на живых запусках, точка отката;
  - `develop` — интеграция, ветка по умолчанию на GitHub, **с неё деплой**;
  - `feature/<kebab-name>` — от `develop`;
  - `hotfix/<kebab-name>` — от `production`.
  - Release-веток нет.
- **Фича:** ветка от `develop` → коммиты → `gh pr create --base develop` → `gh pr merge --merge --delete-branch` (вливает Claude сам) → `develop` → `scripts/deploy.sh` → проверка на живых запусках.
- **Релиз:** PR `develop` → `production` с заголовком `chore(release): vГГГГ.ММ.ДД` → merge → тег `vГГГГ.ММ.ДД` (второй за день — `.2`) на `production`.
- **Hotfix:** `hotfix/*` от `production` → PR в `production` → деплой с `production` → тег → PR `production` → `develop` → снова деплой с `develop`.
- **Защита в `deploy.sh`:** с другой ветки деплой не запустится без `--any-branch`. Если есть незакоммиченные изменения, скрипт предупредит.
- **Откат:** `git switch production && scripts/deploy.sh`.
- **Репозиторий:** `git@github.com:hello-kozloff/job-hunter.git`, приватный. До 07.10.2026 основная ветка называлась `main`.
